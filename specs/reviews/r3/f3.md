Finding: r3.f3
Claim: fixed
Change: `scripts/cloud/bake.sh` reads `lock.sh bake-args` with `output="$(...)"` instead of `mapfile -t args < <(...)`, so a bake-args that exits non-zero (after printing some lines, as on an unknown line kind) stops bake.sh with that status under `set -e` and `inherit_errexit`, before docker is called; the output is split into `--set` values only after it succeeded. The empty-output check stays: a bake-args that exits 0 with nothing would build with no lock. The deploy's "Build settings" step already reads it as `lock="$(...)"` under `set -euo pipefail`, so it fails closed and is unchanged
Evidence: `tests/unit/test_bake_script.py`: restoring the `mapfile` read fails `test_a_lock_that_fails_after_printing_builds_nothing` (a lock with `go - 1.27.0` after the claude line, the real trigger) and `test_the_status_of_a_failing_lock_is_the_status_of_bake` (a fake lock.sh that prints two lines and exits 7); disabling the empty-output check fails `test_a_lock_that_prints_nothing_builds_nothing`
