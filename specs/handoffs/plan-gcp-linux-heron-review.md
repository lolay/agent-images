Runs the `linux` runner type on Cloud Run, end to end: m1 of `specs/gcp.md`, on the foundation `lolay/infrastructure` (`stacks/gcp/agents`) already applied. A push to `main` builds the images, smoke-tests `agent-linux-next`, promotes `agent-linux`, and points the orchestrator VM at the new orchestrator image. Plan: `specs/handoffs/plan-gcp-linux-heron.md`.

**Before merging:** create the `production` environment with a main-only branch policy (fish commands in the handoff). GitHub would otherwise create it on first use with no policy. The first push deploys everything.

<details open><summary><b>[study]</b> hook, supervisor, deploy workflow</summary>

- **[`hooks/gcp/spawn-runner`](https://github.com/lolay/agent-images/compare/main...claude/eloquent-mayer-ivkml8#diff-d55d84a6c00a97f4b35fc94450ad76c6cdc1b30877742aa473100fd750189a8f)**: creates `orders/<id>` with `ifGenerationMatch=0` (a 412 means the order already has an execution), then calls `POST jobs/agent-<type>:run` with the work order and label as container env overrides on container `runner`. Any failure after the marker deletes it. 403 and 404 return exit 2 (don't retry); everything else returns 1. [`hooks/gcp/lib.sh`](https://github.com/lolay/agent-images/compare/main...claude/eloquent-mayer-ivkml8#diff-d3a896346666abbb21d9ac8428e17793c525b995d6c602d6135e8ea9ec20d250) passes the token as a header through a file descriptor; the body goes on stdin, built by `jq --rawfile`. Tests check that the work order appears only in the run body.
- **[`images/cloud/orchestrator/supervisor.sh`](https://github.com/lolay/agent-images/compare/main...claude/eloquent-mayer-ivkml8#diff-86b923fda9ba7c1579777c90696a730322c7eb7470fc44c73b5199bac50fc50e)**: one loop owns every child through `wait -n`. Each signal is forwarded once, from the trap and again at the top of the loop, so an orchestrator whose start the signal interrupted is stopped too; the test for this hangs against the trap-only version. Every pass also collects children that are no longer running. Secrets go to `/dev/shm`, mode 600, one file per type. Orchestrators drain for 70 s inside docker's 85 s.
- **[`.github/workflows/cloud-deploy.yml`](https://github.com/lolay/agent-images/compare/main...claude/eloquent-mayer-ivkml8#diff-87020c72ebdd73ecb05e14a3673b1a63b4cb58fd96acea002a0f9dc91885bc7e)**: `plan` has no `id-token` and diffs against the last successful push deploy (GitHub's queue cancels pending runs, so `before` would drop their pushes). `types`, `orchestrator` and `prune` run in `production`. <details><summary>Decisions</summary>

- Jobs are written through the Cloud Run v2 REST API (`PATCH` with `allowMissing`): gcloud can't make a disk-backed volume.
- No gcloud on the orchestrator host: the hook and supervisor use REST with a metadata-server token.
- Claude upgrades itself at runner start until m4's watch exists, or the session test's version check fails after each release.
- No standby in m1. No `cloud-publish` or `cloud-promote`: only `main` deploys.
- Rotating a key means resetting the VM: its unit ignores a metadata value equal to the running image.
- First-deploy risk: if Cloud Run rejects `DISK` for jobs, try `LAUNCH_STAGE=BETA` in `linux.env`.

</details>
